# 代码评审

## 输入准备

先拿到真实改动，不要凭猜测评审：

```bash
git status --short
git diff --stat
git diff            # 未暂存改动
git diff --cached   # 已暂存改动
```

没有 git 仓库时，直接用 read_file 读取用户指定的文件。

## 评审顺序（按重要性递减）

1. **正确性**：逻辑是否与意图一致？条件判断、循环边界、异步等待、错误分支是否处理？
2. **边界与异常**：空值、空数组、超长输入、并发、网络失败、文件不存在。
3. **安全**：SQL 注入、XSS、路径穿越、密钥硬编码、权限校验缺失、依赖已知漏洞。
4. **性能**：N+1 查询、循环内 I/O、不必要的全量复制、缺失索引/缓存。
5. **可维护性**：命名、重复代码、函数长度、魔法数字、注释是否说明「为什么」。

## 输出格式

按严重程度分组，每条给出 `文件:行号`、问题、建议改法：

```
### 必须修（阻塞合并）
- `src/api/user.ts:42` 未校验 userId 来源，存在越权风险 → 增加归属校验

### 建议修
- `src/utils/parse.ts:18` 空字符串会走到 NaN 分支 → 提前 return

### 可选优化
- `src/db/query.ts:77` 循环内逐条 insert → 改为批量
```

## 规则

- 只报告有证据的问题，附具体行号；不确定的标为「疑问」而非「缺陷」。
- 不要为了凑数而提无关痛痒的风格问题。
- 改动较多时先给总体评价（3 句话内），再列细节。
- 发现安全问题时，明确标注风险等级与触发条件。
